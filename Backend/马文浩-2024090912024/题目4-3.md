# 4-3 优化历史洪流

### 一、“档案馆结构优化”（表结构设计）

- **添加索引**：在 `status` 字段上创建索引。创建索引后，使用引擎自带的B+树查找，而不需要全表扫描。

```sql
Create index idx on orders (status);
```

- **分表（可选，若数据量持续增长且单表压力极大）**：如果数据量未来还会大幅增长，可考虑按 `status` 进行分表。比如创建 `orders_paid`（存储 `status = '已支付'` 的订单）、`orders_unpaid`（存储 `status = '待支付'` 的订单）、`orders_cancelled`（存储 `status = '已取消'` 的订单）等表。这样查询 `已支付` 订单时，只需查询 `orders_paid` 表，数据量减少，查询速度加快。

### 二、“咒语咏唱技巧”（SQL 查询优化）

- **避免使用 `SELECT *`**：`SELECT *` 会查询表中所有字段，若表中有大量不相关字段，会增加数据传输量和查询时间。应明确指定需要的字段，例如如果只需要 `id`、`user_id`、`product_name`，可以写成：

```sql
select id, user_id, product_name from orders where status = '已支付';
```

### 三、借助外部 “魔法奇物”（如 Redis 缓存）协同加速

- **缓存热点数据**：对于 `status = '已支付'` 的订单这类热点数据，可将查询结果缓存到 Redis 中。当再次查询时，先从 Redis 中获取，如果 Redis 中没有，再去 MySQL 查询，并将结果同步到 Redis。这样可以减少对 MySQL 的直接查询压力，提高查询速度。
- **设置合理的缓存过期时间**：根据业务场景，设置 Redis 缓存的过期时间。例如，如果订单状态更新不频繁，可设置较长的过期时间；如果订单状态更新较频繁，则设置较短的过期时间，保证数据的时效性。
